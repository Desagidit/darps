# Briefing-summary caching plan

## Goal

Avoid repeating optional briefing-summary calls when their exact authorized
source has not changed.

This is a future feature, not current behavior. It is deliberately narrower
than caching complete character prompts.

## Implemented precursor: compiled knowledge routing

The static common-knowledge problem is now handled separately from dynamic
briefing summaries. `darps compile-knowledge` writes an inspectable,
source-hashed routing catalogue for common, ungated `shared_knowledge`.
With `knowledge_cache` enabled, the semantic resolver sees compact routing
labels generated by a separately configurable author-time model and maps
selected labels back to exact live YAML.

This does not cache a generated briefing, does not enter session state, and
does not make generated prose authoritative. Missing or invalid artifacts
fall back to the original full-corpus resolver. Conditional knowledge and
world summarisation remain outside this implemented precursor.

## Why not cache final briefings

A final briefing varies with:

- player message and shared-knowledge relevance;
- current location and accessible items;
- flags and `when` gates;
- learned facts and canon;
- current track prose band;
- conversation history.

Learning no new fact does not prove that the next briefing is equivalent.
Caching a complete prompt would therefore create difficult invalidation bugs
and possible context leaks.

## Proposed design

Cache only generated compression artifacts. Key each entry by a stable hash
of:

- exact authorized source text;
- character ID;
- compression level and target budget;
- summary prompt contents/version;
- summary model/provider configuration;
- pack identity.

Any pack edit, gate change, fact/canon/history change, model change, or prompt
change naturally produces a new key. This retains hot reload without a manual
invalidation matrix.

The cache should be session-local initially. Cross-session reuse can be
considered only for demonstrably session-independent source text.

## Rolling history

Do not indefinitely summarize a summary. Incremental history compaction can
be used for short intervals, but periodically rebuild from authoritative
conversation records to prevent accumulated distortion.

If an old-history summary becomes the only retained memory, it stops being a
mere cache and becomes session state. That later design would require:

- a versioned state field;
- restore normalization;
- persistence tests;
- a clear policy for how much source history remains available for rebuild.

The first implementation should remain discardable and rebuildable.

## Provider prompt caching

Provider-side prefix caching is a separate optimization. Stable prompt-prefix
ordering may reduce cost and latency, but it does not reduce context length.
Keep this independent from semantic compression and do not make core behavior
depend on provider-specific cache controls.

## Tests

- Identical exact sources reuse one summary.
- Any relevant source/config/prompt change misses the cache.
- One character/session can never retrieve another's dynamic summary.
- Cache eviction changes performance only, never prompt semantics.
- Pack hot reload invalidates affected summaries.

## Open decisions

- In-memory LRU size and eviction policy.
- Whether static, session-independent summaries may be shared across sessions.
- Whether cache metrics belong in call logs or a separate diagnostics endpoint.
